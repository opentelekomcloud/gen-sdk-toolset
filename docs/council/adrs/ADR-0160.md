Endpoints of one version are first grouped by the first static segment of the URI after the version segment (if there is one) and after path parameters such as {project_id}. A group that contains more than half of the version's endpoints is split by the next static segment. If all endpoints of the group that have a next static segment share the same one, the layout skips it and splits the group by the first segment where the endpoints differ. An endpoint whose static segments run out earlier stays in a resource named after its last static segment. Splitting repeats until no group exceeds the threshold or until the endpoints of a large group run out of static segments. The segment that gave the resource its name is converted to lower case, invalid characters in it are replaced with "_", and if the name does not start with a letter, the prefix "r_" is added to it. Endpoints with the same resource name and the same part of the URI before the name segment go to one resource. Endpoints without a static segment after the version go to the "unassigned" list of their version, and the user moves them from there to resources, because only groups that contain more than half of the version's endpoints are split. So services where the first static segment already splits the endpoints keep a few resources with short names, close to the services/<service>/<version>/<resource> packages in python-t-cloud. For services like api-gateway, the common apigw segment and the common segments after it are skipped, and the endpoints are split into resources where their URIs actually differ.
