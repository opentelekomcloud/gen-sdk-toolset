The default SDK method name is built the same way wherever the segment that gave the resource its name is located. A basic operation gets the name create, get, list, update or delete. A custom operation gets the name of the last static segment of the URI. For a nested path, the static segments of the URI after the first static segment (after the version segment and path parameters) are added to the name with "_", for example list_routes or tags_action. In the name of a basic operation on an item, the last segment is singular, for example delete_tag. If PUT and PATCH operations on the same item would both get the name update, the PATCH operation gets the name patch. All default names in one resource are distinct: the rule that tells matching names apart, including the names of operations with different URIs, is defined before implementation from the data of all services. Operations of one resource from different documents with the same HTTP method and URI get no default name: the name stays empty until the user enters it. Resource generation does not start while any of its operations has no name. The same applies to operations whose default names still match after the rule that tells them apart is applied. The user can enter the same name to combine operations into one SDK method, because the point from which segments are counted does not depend on where the resource segment is located or on what other endpoints the resource has. So moving an endpoint does not shift the names of the other operations of the resource, and their manual edits are not deleted because the default name changed. The default names in already laid-out resources and the code that builds them stay the same.
