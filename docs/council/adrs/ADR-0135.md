Endpoints of one version are first grouped by the first static URI segment. Static segments are counted after the version segment if the URI has one, and path parameters such as {project_id} are skipped. A group that contains more than half of the version's endpoints is split by the next static segment. Endpoints of such a group that have no next static segment stay in a resource named after the current segment. Splitting repeats until no group exceeds the threshold or until a large group cannot be split: all its endpoints have the same next static segment, or none of them has one. The resource name is the segment in lowercase, with invalid characters replaced by “_”; if the name does not start with a letter, the prefix “r_” is added to it. Endpoints without a static segment after the version do not get an invented name; they go into the “unassigned” list of their version, from which the user moves them into resources, because the layout itself splits only a segment that is shared by almost all endpoints of the version. So the user does not need to know the URI structure in advance, and where the first segment already gives small groups, resources stay few and have short names, like the services/<service>/<version>/<resource> packages in python-t-cloud. The explicit stop condition guarantees that splitting ends and that no endpoint drops out of the layout.
