# FAQ — how to do the common things

Worked examples for changing the code. Running the scanner and the test suite
is covered in [README.md](../README.md); this file starts where that one stops.

If a task you did is missing here and took you more than one attempt, add it.

## How do I add a new issue code?

An `IssueCode` is part of the output contract; adding one is cheap, but adding
one that can never fire is worse than not adding it.

1. Add the member to `IssueCode` in `src/tools/shared/scan/issue.py`, in the
   group it belongs to.
2. Emit it where the condition is detected — attach `location` and `details`,
   because a bare code tells the reader nothing about which table or field.
3. Add it to `docs/GLOSSARY.md` if it introduces a new concept.
4. Add a test that produces it from a real fixture. This is the important step:
   it proves the code is reachable. A declared code with no test that triggers
   it will report `0` forever and be read as "this never happens".

## How do I add support for a new parameter table shape?

The parsing code lives in `src/tools/scanner/parsers/docutils/`, split by
concern — `table.py`, `nesting.py`, `references.py`, `field_type.py`,
`example.py`, `routing.py`.

1. Capture the real document as a fixture: put the `.rst` in `tests/fixtures/`,
   named `style_<a|b>_<service>_<what_is_special>.rst`, and add a loader fixture
   to `tests/conftest.py` alongside the existing ones.
2. Write the failing test first, asserting the `Parameter` tree you expect.
3. Implement, and decide explicitly what happens to rows you still cannot read:
   they must produce an `Issue` and count into `fields_failed` or
   `fields_unknown_type` — never silently vanish from `fields_total`.
4. Check the counters still reconcile. The validator on `SectionScanResult` will
   tell you if they do not.

## How do I add an endpoint to the panel API?

1. Response and request models go in `src/tools/panel/api/schemas.py`.
2. The route goes in `src/tools/panel/api/routes/`, using
   `db: Session = Depends(get_db)` for a request-scoped session.
3. Raise `HTTPException`; the envelope in `src/tools/panel/api/errors.py` turns
   it into the consistent `{"error": {"code", "message"}}` shape. Do not build
   error bodies by hand.
4. Register the router in `src/tools/panel/api/app.py` under the `/api` prefix.
5. Regenerate the schema and the frontend types, and commit both:

```bash
uv run panel openapi > src/tools/panel/openapi.json
cd frontend && npm run gen:types
```

`panel openapi` prints to stdout, so the redirect is the command - running it
without one changes nothing. The frontend types are generated from that file;
skipping this step is how the two sides drift.

## How do I change the database schema?

Never edit a migration that has already been applied. Add a new revision:

```bash
uv run alembic revision --autogenerate -m "add x to y"
uv run alembic upgrade head
```

Read the autogenerated file before committing it — Alembic misses CHECK
constraints, partial indexes and enum changes, which is exactly the sort of
thing this schema relies on. Add a test in `tests/test_panel_db.py` that proves
the new constraint rejects what it should reject.

## How do I run a long operation without blocking the API?

The pattern is in `src/tools/panel/core/jobs.py`: create the job row and
**commit it before** scheduling the background task, so the ID exists no matter
what happens next; return immediately with the ID; then, in the background,
open your own session, read what you need into local variables, commit the
status change, and let the session close *before* doing the slow provider work.

The reason the session closes first is not tidiness: an open transaction held
across a network call will hold locks for the length of the scan, and a lazy
attribute load after the commit would quietly reopen one.

## The numbers look wrong. Where do I start?

Numbers in the panel come from the analytics functions - `tools.domain.report`
today, moving to `tools.panel.core.analytics` with #34 - computed from the
nested scan results. In order:

1. Run the scanner on a pinned SHA and read the raw JSON, not the panel.
2. Look for impossibilities rather than for wrong values: a declared
   `IssueCode` with zero occurrences across thousands of documents, counts that
   do not reconcile (`ok + partial + failed + unsupported` against the document
   total), buckets split by case or by a trailing slash, suspicious names in
   `excluded_documents`.
3. When something looks wrong, fetch a handful of the actual documents behind it
   and check the hypothesis before projecting a rate. The first sampling
   heuristic always overcounts.
4. Close the finding with a test, not only with a fix.

## Where do I put a plan or a review?

Neither is committed. Plans live outside the repository; review output lives in
the session or in the pull request. What survives a review is the fix and the
guard that stops it coming back — a test, a lint contract, an assertion.

The one thing that must reach the repository is the *link*: an issue number,
referenced from the code that is waiting on it (`# TODO(#23):`,
`NotImplementedError("... — see #23")`). That number is the only part of a plan
another person's tooling can see.
